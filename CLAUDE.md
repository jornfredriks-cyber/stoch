# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working in this repository.

## Project Overview

Standalone toolkit implementing the "Weekly Stochastic Sweet Spot" trend-following strategy (`Weekly Stochastic Sweet Spot Strategy.md`, sourced from a YouTube video — treat it as reference material, don't edit it with derived analysis). Originally built inside `Darvas Phase3 Scan/`, relocated to its own project with its own venv/config/tests on 2026-07-14 so it has no dependency on that project.

Three-stage pipeline, same shape as `Darvas Phase3 Scan/`:

| Stage | Script | Purpose | Output |
|---|---|---|---|
| 1 | `screener.py` | Pre-filter NASDAQ+NYSE universe (price/volume/EMA/ADR/RSI/ATH) | `OUTPUT/Screener/Stoch Raw Screener_YYYY-MM-DD.csv` |
| 2 | `stoch_scan.py` | Live scan: flag tickers currently inside the 32–80 sweet-spot band, %K>%D, rising | `OUTPUT/SweetSpot/Stoch_SweetSpot_YYYY-MM-DD.txt` |
| 3 | `backtest.py` | Backtest the strategy's long entry/exit rules against full historical data | `OUTPUT/Stoch_Backtest_Trades_YYYY-MM-DD.csv` |
| 3b | `backtest_signal.py` | Separate backtest of the "Stochastic Weekly Signal" Pine indicator's exact crossover/crossunder circle events (fixed $1000/trade, no SL/TP). Universe: newest file in `INPUT/` if one exists (any name/format), else the Darvas Raw screener CSV — **different rule set from `backtest.py`**, see below | `OUTPUT/StochSignal_Backtest_Trades_YYYY-MM-DD.csv` |
| 3c | `backtest_signal_sweep.py` | Parameter sweep: grid-searches `stoch_length`/`k_smooth`/`d_smooth` (entry/exit thresholds fixed at 32/80) on top of `backtest_signal.py`'s exact rule set, ranks combos by total $ P&L | `OUTPUT/StochSignal_Sweep_YYYY-MM-DD.csv` |
| 4 | `stoch_signal_scan.py` | Live buy-candidate scan: same exact crossover rule as `backtest_signal.py` (fired on the **latest** weekly bar) **plus** an `is_not_stretched()` gate (current daily close within 0-5% above daily EMA50 — not chasing an extended move), against the Darvas Raw screener universe | `OUTPUT/StochSignal_Candidates_YYYY-MM-DD.csv` |
| 3d | `backtest_signal_sltp_sweep.py` | Adds an SL/TP overlay + optional weekly EMA50>EMA200 long-term trend filter on top of `backtest_signal.py`'s exact crossover rule; sweeps SL 4-10% × TP 1.5-3.5R × filter on/off (70 combos), ranks by total $ P&L, includes a per-ticker win/loss breakdown + trade-level CSVs for the top 3 combos | `OUTPUT/StochSignal_SLTP_Sweep_YYYY-MM-DD.md` |
| 4b | `stoch_fresh_scan.py` | One-operation live buy-candidate scan (`screener.py` → `stoch_fresh_scan.py`, same shape as stage 1→2): flags tickers whose weekly %K crossed strictly above `entry_level` (default 32) within the last `lookback_weeks` (default 2) **fully completed** weekly bars — the current, still-forming week is always excluded — with %K>%D on that bar. Uses Stoch's own screener universe, not the Darvas one; no EMA50 "not stretched" gate | `OUTPUT/Screener/Stoch Raw Screener_YYYY-MM-DD.csv`, `OUTPUT/StochFresh_Candidates_YYYY-MM-DD.csv` |

## Running

```bash
cd "Stoch"

# Live scan pipeline (screener → sweet-spot scan)
venv/bin/python3 screener.py && venv/bin/python3 stoch_scan.py
# or double-click "RUN Stoch Sweet Scan.command"

# Backtest (reads ticker list from INPUT/, or falls back to the screener CSV)
venv/bin/python3 backtest.py
# or double-click "RUN Stoch Backtest.command"

# Signal backtest (reads the newest file in INPUT/ if present, else the Darvas
# Raw screener CSV -- fixed $1000/trade)
venv/bin/python3 backtest_signal.py
# or double-click "RUN Stoch Signal Backtest.command"

# Signal parameter sweep (finds best stoch_length/k_smooth/d_smooth by total $ P&L)
venv/bin/python3 backtest_signal_sweep.py
# or double-click "RUN Stoch Signal Sweep.command"

# Live buy-candidate scan (always reads the Darvas Raw screener CSV; fresh
# crossover + not-stretched-above-EMA50 gate)
venv/bin/python3 stoch_signal_scan.py
# or double-click "RUN Stoch Signal Scan.command"

# SL/TP + long-term trend filter sweep on top of backtest_signal.py's rule
# (reads the same INPUT/-or-Darvas universe as backtest_signal.py)
venv/bin/python3 backtest_signal_sltp_sweep.py
# or double-click "RUN Stoch Signal SLTP Sweep.command"

# Live fresh-buy-candidate scan, one operation (Stoch's own screener → fresh
# crossover within the last 2 completed weeks, no EMA50 gate)
venv/bin/python3 screener.py && venv/bin/python3 stoch_fresh_scan.py
# or double-click "RUN Stoch Fresh Scan.command"

# Tests
venv/bin/python3 -m pytest tests/ -v
```

## Configuration

All tunable parameters live in `stoch_config.ini` — don't hardcode values in the Python files.

- `[screener]` — pre-filter thresholds (price, market cap, volume, ADR, EMA trend, RSI, ATH proximity). Mirrors Darvas Phase3 Scan's screener defaults.
- `[stoch_scanner]` — Stochastic settings (`stoch_length`/`stoch_k_smooth`/`stoch_d_smooth`, currently 19/4/4 — the strategy doc's original settings. Briefly swapped to the `backtest_signal_sweep.py`-optimized 3/7/7 combo on 2026-07-23, reverted back to 19/4/4 on 2026-07-30 — this is the current, intentional setting) and the sweet-spot band (`stoch_k_min`=32.0, `stoch_k_max`=80.0). **`backtest.py` and `backtest_signal.py` both read these same constants from `stoch_scan.py` — there is no separate `[backtest]` section.** The 32/80 band doubles as both backtests' entry/exit levels — they share the same Stochastic settings, only the crossing rule differs (see below).
- `[backtest_signal]` — `trade_value_usd` (default 1000.0), the fixed dollar notional `backtest_signal.py` assumes per trade (no share-count rounding: `dollar_pnl = trade_value_usd * (exit_price / entry_price - 1)`).
- `[stoch_signal_scan]` — `ema_length`/`ema_band_min_pct`/`ema_band_max_pct` (50 / 0.0 / 5.0) for `stoch_signal_scan.py`'s `is_not_stretched()` gate: current daily close must sit within this % band above its daily EMA(`ema_length`). Retired `ema50_screener.py`'s standalone full-market pre-filter (2026-07-26) folded into this one check — the Darvas Raw screener already handles price/volume/ADR/market-cap/trend/RSI/ATH-proximity quality upstream, so only the genuinely new idea (EMA-proximity) needed to move over.
- `[stoch_fresh_scan]` — `lookback_weeks`/`entry_level` (2 / 32.0) for `stoch_fresh_scan.py`'s crossover check: %K must cross strictly above `entry_level`, with %K>%D, within the last `lookback_weeks` fully completed weekly bars (current, still-forming week always excluded). `entry_level` is independent of `[stoch_scanner]`'s `stoch_k_min` (same value today, but a distinct concept — an entry-crossover threshold vs. a persistent-band floor). No EMA/not-stretched keys here — this scan has no such gate, unlike `[stoch_signal_scan]`.
- `[backtest_signal_sltp_sweep]` — `ema_long_fast`/`ema_long_slow` (50/200), the fixed periods for `backtest_signal_sltp_sweep.py`'s optional `"long_trend"` entry filter (weekly EMA50>EMA200 — a regime-level check, ~1yr vs ~4yr; replaced an earlier short EMA10>EMA20 crossover, see Architecture below). The SL/TP grids themselves (`SL_GRID`/`TP_GRID`/`FILTER_GRID`) are **module-level constants at the top of the script**, not in this config section — same convention as `backtest_signal_sweep.py`'s stoch-param grids (a sweep's input space, not a single tunable).

## Architecture

**`scan_utils.py`** — shared utility layer, no strategy logic:
- `fetch_ohlc_bulk(yf_symbols, period=HISTORY_PERIOD, auto_adjust=True)` — chunked yfinance download with retry. `period` defaults to `"1y"` (what `screener.py`/`stoch_scan.py` need) but `backtest.py`/`backtest_signal.py` override it to `"max"` for full history. `auto_adjust` defaults to `True` (splits + dividends fully adjusted, matching `screener.py`/`stoch_scan.py`/`backtest.py`'s long-standing behavior) — `backtest_signal.py` passes `auto_adjust=False` instead (split-adjusted only). See the dividend-adjustment note under `backtest_signal.py` below for why.
- `fetch_ohlc_single`, `find_latest_csv`, `_Tee` (stdout+logfile tee)
- `find_ticker_list(input_folder, fallback_folder)` — resolves the ticker universe. Looks in `input_folder` (i.e. `INPUT/`) for a file matching `*Watchlist*` **or** TradingView's actual default export naming `[Tt]radingview*` (confirmed in practice: `Tradingview <ListName>_<date>_<id>.txt` — it never contains the word "Watchlist"). Falls back to the latest `*Screener*.csv` in `fallback_folder` if neither is found. Only `backtest.py` uses this today — `screener.py`/`stoch_scan.py` still read the screener CSV directly.
- `_parse_watchlist_line(line)` — parses `EXCHANGE:TICKER,EXCHANGE:TICKER` (TradingView watchlist export format), converting `OSLO:` to a `.OL` yfinance suffix. Same convention as `Dashboard/data_loader.py`'s `parse_ticker_line`.

**`stoch_scan.py`** — live scanner + the shared Stochastic math:
- `compute_kd(df, stoch_length, k_smooth, d_smooth)` — resamples daily OHLC to Friday-anchored weekly bars and computes %K/%D. Returns a DataFrame (`close`, `k`, `d`) indexed by weekly bar. The final (possibly still-forming) week is included as-is, matching how TradingView plots a live weekly Stochastic — deliberate, not an oversight. `backtest.py` reuses this directly so the backtest and live scan always agree on the math.
- `is_stoch_sweet_spot(df, ...)` — calls `compute_kd`, then checks: latest %K inside `[k_min, k_max]`, %K > %D, %K rising vs. `k_rising_lookback` weeks back. Returns `(True, k, d)` or `(False, None, None)`.

**`backtest.py`** — trade simulation:
- `simulate_trades(weekly, entry_level=32.0, exit_level=80.0)` — pure function, no I/O. Takes a `compute_kd`-shaped DataFrame and returns a list of trade dicts. State machine, confirmed rules (see below). Fully unit-tested in isolation from OHLC/resampling concerns.
- `run_backtest(folder)` / `main()` — orchestration: `find_ticker_list` → `fetch_ohlc_bulk(period="max")` → `compute_kd` → `simulate_trades` per ticker → CSV + log + console summary. Wraps the per-ticker loop in try/except (one bad ticker doesn't abort the run) and de-dupes the ticker list before processing (a duplicate ticker would otherwise double-count its trades into the win-rate stat).

### Confirmed backtest rules (long-only)

- **Entry**: first week %K crosses above 32 (prior week <32, current week ≥32). Pure %K level-cross — %D not checked. Fill at that week's close.
- **Exit**: first week *after entry* where %K < %D **and** %K < 80 are simultaneously true. This holds through %K≥80 even if %K has already crossed below %D ("ride it"), and holds below 80 as long as %K stays above %D. Fill at that week's close.
- No stop loss. No portfolio/capital simulation — each trade is an isolated % return. A ticker can produce multiple sequential trades over its history.
- Still-open positions when data ends are recorded as `open`, marked-to-market at the last close, excluded from win/loss stats.
- **Not yet implemented**: short side, parameter sweep across Stochastic settings, a trailing-stop/breakeven variant of the exit rule (see Open Threads below).

### `backtest_signal.py` — different rule set, do not confuse with `backtest.py`

Backtests the "Stochastic Weekly Signal" Pine indicator's literal `buySignal`/`sellSignal` circle-plot conditions, not the strategy doc's rules above.

- **Ticker universe (`load_backtest_signal_tickers()`, added 2026-07-25)**: if `INPUT/` contains any non-hidden file, uses the newest one by mtime — no filename or content-format requirement (parsed the same way as a watchlist: one ticker per line, or comma-separated `EXCHANGE:TICKER`, via `_parse_watchlist_line`). This is deliberately looser than `scan_utils.find_ticker_list()`'s `*Watchlist*`/`[Tt]radingview*`-only glob (used by `backtest.py`) — drop in e.g. a hand-picked ticker list `.txt` as-is, no renaming needed. Falls back to the latest `DARVAS Raw Screener_*.csv` in `../Darvas Phase3 Scan/` (via `find_latest_csv`) if `INPUT/` has no files, same as this script's behavior before `INPUT/` support existed.

- **Entry (green)**: %K crosses *strictly* above `stoch_k_min` (prior week %K < 32, current week %K > 32) **and** %K > %D on the current week.
- **Exit (red)**: %K crosses *strictly* below `stoch_k_max` (prior week %K > 80, current week %K < 80) **and** %K < %D on the current week.
- No stop loss, no take profit. Fixed `trade_value_usd` (1000.0) notional per trade — `dollar_pnl` reported alongside `return_pct`.
- **Quirk, not a bug**: because exit requires an actual crossunder-of-80 event, a trade whose %K never climbs back above 80 after entry will never get an exit signal under this literal rule and stays `open` until the ticker's data ends. Expect a non-trivial open-trade count in the summary — that's this rule doing what the Pine source says, not a broken backtest.
- `simulate_trades_signal()` is intentionally a separate function from `backtest.py`'s `simulate_trades()` — same state-machine shape, different (stricter, event-based) crossing conditions. Don't merge them; they answer different questions.
- **Raw chart circles will outnumber the trade log — expected, not a discrepancy.** The Pine indicator's `plotshape()` draws a circle every time the raw `buySignal`/`sellSignal` condition is true, with no memory of position state. `simulate_trades_signal()` deliberately only counts the *first* green after being flat and the *first* red after being long (ignoring buy signals that fire while already holding, and sell signals that fire while already flat) — matching the single-position, $1000-no-pyramiding framing the backtest was built for. Verified 2026-07-21 on AAPL/weekly (`periodK=3,smoothK=7,periodD=7`): raw signals included extra BUYs on 2022-06-24/2022-10-28 (already holding since 2021-04-09, correctly ignored) and extra SELLs on 2023-12-29/2025-10-10 (already flat, correctly ignored) — only 2023-07-14, 2024-04-26/07-19, and 2026-04-10/06-12 made it into the actual trade list. When eyeballing the indicator against a CSV trade log, expect this gap and don't treat it as a bug.
- **Dividend-unadjusted prices (`auto_adjust=False`)**: unlike every other script in this project, `backtest_signal.py` fetches with `auto_adjust=False`. Confirmed by manual verification (2026-07-21) against the live TradingView indicator on ABBV: `auto_adjust=True` (the project default) fully adjusts historical OHLC for dividends as well as splits, and ABBV alone has paid 55 dividends since 2013 with zero splits — the adjustment ratio drifts over time (e.g. 0.64 in Nov 2015 vs 0.67 in Nov 2016, since `auto_adjust=True` rescales the whole history relative to *today's* cumulative dividends every time it's fetched). This measurably shifted the Stochastic's rolling-window %K/%D, causing wrong exit weeks and fully missed trade cycles versus what the chart actually plots (TradingView shows raw/unadjusted prices by default). Switching to `auto_adjust=False` (split-adjusted only — verified against AAPL's Aug 2020 4:1 split showing no price discontinuity) resolved 4 of 5 discrepancies found in that ABBV spot-check exactly, and reduced the 5th from ~17 days off to ~10 days off (residual gap likely Yahoo-vs-TradingView data-vendor differences in daily H/L, not adjustment). This fix is scoped to `backtest_signal.py` only — `backtest.py`/`stoch_scan.py`/`screener.py` still use the default `auto_adjust=True`, so their previously-documented results (see Open Threads below) are unaffected.

### `stoch_signal_scan.py` — live buy-candidate scan, same rule as `backtest_signal.py`

Answers "which Darvas Raw screener tickers have a fresh buy signal *right now*, that isn't already an extended move," instead of backtesting full history. Reuses `backtest_signal.load_darvas_raw_tickers()` and `stoch_scan.compute_kd()` directly — no duplicated math.

- `is_fresh_stoch_signal_buy(df, ...)` — checks only the **last two valid weekly bars**: prior bar's %K < 32, current bar's %K > 32 (strict), %K > %D on the current bar. Same entry condition as `simulate_trades_signal()`'s buy leg, but evaluated once against the latest bar instead of iterating the full trade history — deliberately cheaper than running the whole state machine just to answer a "did it fire this week" question. Returns `(True, k, d, entry_date, entry_price)` or `(False, None, None, None, None)`.
- `is_not_stretched(df, ...)` (added 2026-07-26) — the surviving idea from the retired `ema50_screener.py` supplement (see Open Threads below): requires the current daily close to sit within `ema_band_min_pct`-`ema_band_max_pct`% (default 0-5%) above its daily EMA(`ema_length`, default 50). Drops any trailing NaN close row first (the yfinance `auto_adjust=True` gotcha from 2026-07-25 — see `feedback-yfinance-trailing-nan` memory). A candidate only makes the final list if **both** `is_fresh_stoch_signal_buy()` and `is_not_stretched()` pass — the CSV output includes `ema50_dist_pct` so you can see how close each survivor actually is.
- Buy-only by design: sell signals only matter for positions actually held, and this scanner has no notion of your holdings.
- Same `auto_adjust=False` fetch as `backtest_signal.py`, same rationale (unadjusted prices match what the live Pine indicator actually plots) — this is a separate fetch from the trailing-NaN issue above, which is specific to `auto_adjust=True` fetches elsewhere in the project.
- Ticker universe freshness: like every other script here, it just takes whichever `DARVAS Raw Screener_*.csv` is newest by file mtime — re-run `../Darvas Phase3 Scan/darvas_screener.py` yourself first if you want a same-day universe.
- Output: `OUTPUT/StochSignal_Candidates_YYYY-MM-DD.csv` (`ticker`, `entry_date`, `entry_k`, `entry_d`, `price`, `ema50_dist_pct`) — one row per fresh, not-stretched candidate, no historical trades.

### `stoch_fresh_scan.py` — one-operation fresh-crossover scan, Stoch's own universe

Answers "which of Stoch's own screener candidates had a fresh weekly Stochastic buy crossover in the last week or two — not just this exact instant?" A sibling to both `stoch_scan.py` (same engine: `compute_kd()`, `[stoch_scanner]` settings, Stoch's own screener output) and `stoch_signal_scan.py` (same crossover-event shape), but combining traits neither one has alone.

- `is_fresh_stoch_buy_within_lookback(df, ..., entry_level, lookback_weeks)` — checks the last `lookback_weeks` **fully completed** weekly bars (default 2) for a strict crossover: prior week's %K < `entry_level`, that week's %K > `entry_level`, %K > %D on that week. **The current, possibly still-forming week is always dropped before any check runs** (`kd.iloc[:-1]`, done before `dropna()` so a NaN live bar can't be mistaken for a real completed week) — this is the key behavioral difference from `stoch_signal_scan.is_fresh_stoch_signal_buy()`, which deliberately treats the live bar as eligible. If more than one week in the window qualifies, the most recent one wins. Returns `(True, k, d, entry_date, entry_price, weeks_ago)` or `(False, None, None, None, None, None)`.
- **Universe**: `find_latest_csv(folder)` on the Stoch project root — Stoch's own `screener.py` output, same as `stoch_scan.py` — **not** the Darvas Phase3 Scan project's screener that `stoch_signal_scan.py` depends on. This is what makes `RUN Stoch Fresh Scan.command` a true single self-contained operation (`screener.py && stoch_fresh_scan.py`), unlike `stoch_signal_scan.py` which silently relies on whichever Darvas screener CSV happens to already exist.
- **No EMA50 "not stretched" gate** — a deliberate omission versus `stoch_signal_scan.py`. The only qualifying condition is the fresh crossover itself.
- **Dividend-unadjusted prices (`auto_adjust=False`)**: same fix as `backtest_signal.py`/`stoch_signal_scan.py` (see the dividend-adjustment note under `backtest_signal.py` above), applied here for an independent reason — this scan's whole purpose is precise crossover-*timing* detection, which `auto_adjust=True`'s retroactive dividend rescaling directly corrupts. Confirmed on EQNR (2026-07-30): with `auto_adjust=True`, the real crossover (a clean one-week jump from %K=31.5 to 44.1 per the user's own TradingView export, unadjusted) got smeared across two of our weekly bars — %K crept above 32 a week early but stayed below %D that week, then by the next week %K had already been above 32 too long to register as "fresh" — so the signal was missed by the 2-week lookback entirely, in both directions. Recomputing with `auto_adjust=False` matched the TradingView export almost exactly (%K 44.08 vs. 44.09, %D 34.50 vs. 34.51) and correctly classified it as `weeks_ago=1`. First run under this fix (2026-07-30, 488-ticker screener universe post the user's `ath_max_dist_pct` 5%→10% widening) found 7 candidates: CHRD, SFD, BDX, CF, EPRT, EQNR, WEX — up from 1 (WEX only) under the original `auto_adjust=True` run.
- Buy-only by design, same rationale as `stoch_signal_scan.py`.
- Output: `OUTPUT/StochFresh_Candidates_YYYY-MM-DD.csv` (`ticker`, `weeks_ago`, `entry_date`, `entry_k`, `entry_d`, `price`) — `weeks_ago` placed early since distinguishing a 1-week-old from a 2-week-old signal is the whole point of this scan.

### `backtest_signal_sltp_sweep.py` — SL/TP overlay + trend filter sweep on `backtest_signal.py`'s rule

Answers "does adding a stop-loss/take-profit and a long-term trend entry filter improve on the pure signal-only exit?" Reuses `backtest_signal.load_backtest_signal_tickers()` (same `INPUT/`-or-Darvas universe resolution) and `stoch_scan.compute_kd()`/`resample_weekly()` directly.

- `build_weekly_frame(daily)` — weekly `close`/`k`/`d`/`ema_long_fast`/`ema_long_slow`, computed **once per ticker** and shared across all 70 grid combos (none of the swept parameters change these values, only how `simulate_trades_signal_sltp()` interprets them) — same resample-once-reuse-many optimization as `backtest_signal_sweep.py`.
- `simulate_trades_signal_sltp(daily, weekly, sl_pct, tp_r, filter_type, ...)` — same exact entry crossover as `simulate_trades_signal()`, optionally gated (`filter_type="long_trend"`) by weekly `ema_long_fast > ema_long_slow` (default 50/200, ~1yr vs ~4yr — a regime-level check, not a short-term crossover) on the entry bar. `stop_price = entry_price*(1-sl_pct/100)`; `target_price = entry_price + tp_r*(entry_price-stop_price)` (TP is an **R-multiple of the SL risk**, not a flat %). Once in a position, checks **daily intraweek highs/lows** (not just the weekly close) for the first day whose low breaches `stop_price` or high breaches `target_price` — exits there, at the stop/target price itself. If no daily touch that week, falls through to the original signal exit (`simulate_trades_signal()`'s crossunder-of-80 condition) at that week's close. **Priority: SL/TP touch (checked daily) wins over the signal exit (checked weekly)** — whichever fires first in date order. If a single day's range touches both SL and TP, SL is assumed to hit first (conservative worst-case tie-break; raw OHLC can't reveal true intraday sequencing). Reports `holding_days` instead of `holding_weeks` since exits can now land mid-week.
- Grid: `SL_GRID=[4,5,6,7,8,9,10]`% × `TP_GRID=[1.5,2.0,2.5,3.0,3.5]`R × `FILTER_GRID=["none","long_trend"]` = 70 combinations, all module-level constants at the top of the file (widen/narrow as needed, same convention as `backtest_signal_sweep.py`'s stoch-param grids).
- **2026-07-26 pivot**: the filter was originally a short weekly EMA10>EMA20 crossover (boolean), tested first and found inconclusive on small sample sizes. Replaced with the long-term `EMA50>EMA200` regime filter above after per-ticker analysis showed NOG/EQT's losses cluster inside multi-month/year downtrends, not short-term noise — a regime-level filter targets that directly. `use_ema_filter: bool` became `filter_type: str` (`"none"`/`"long_trend"`) to make room for future filter types without another boolean-to-something rewrite.
- Output: a single markdown file, `OUTPUT/StochSignal_SLTP_Sweep_YYYY-MM-DD.md` — a sweep-results table (all 70 combos, sorted best-first by total $ P&L, with SL/TP/signal exit-reason counts per row) plus a per-ticker wins/losses/win% table for each of the top 3 ranked combos. Trade-level CSVs (`OUTPUT/StochSignal_SLTP_Trades_Rank1/2/3_<date>.csv` — full entry/exit dates, prices, exit reason) are also saved for the top 3, for drilling into individual tickers' trade history.
- Ships with `RUN Stoch Signal SLTP Sweep.command`. 9 tests in `tests/test_backtest_signal_sltp_sweep.py` covering SL-hit, TP-hit, same-day-tie-break, signal-exit-when-no-touch, long-trend-filter gating both directions, R-multiple math, and open-trade mark-to-market.
- **Findings (2026-07-26)**: SL dominates the exit mix (~68% of closed trades in the best combo) — breakeven win rate depends only on the TP multiple (`1/(1+TP_r)`, e.g. 22.2% at TP=3.5R), and a ticker's actual TP-hit rate relative to that threshold determines whether it's a net winner. NOG/EQT sit below breakeven at high TP (structural, not a tuning problem); NVDA sits well above it. The `long_trend` filter **cuts NOG/EQT's loss counts substantially** (e.g. at SL=9%/TP=3.5R: NOG 17→5 losses, flips to slightly positive P&L; EQT 30→19 losses) but also **cuts NVDA's best trades**, shrinking its total $ contribution enough that the filtered aggregate underperforms the unfiltered one overall — the filter helps the weak/choppy names specifically but isn't a free win across a mixed universe.

### `backtest_signal_sweep.py` — parameter sweep on top of `backtest_signal.py`

Grid-searches `stoch_length` × `k_smooth` × `d_smooth` (`LENGTH_GRID`/`K_SMOOTH_GRID`/`D_SMOOTH_GRID` constants at the top of the file — widen/narrow as needed) to find the combo that maximizes **total $ P&L across closed trades** (not win rate) for the same fixed 32/80 entry/exit thresholds and `simulate_trades_signal()` rule set as `backtest_signal.py`. Per user decision (2026-07-21): entry/exit thresholds are held fixed, not swept — only the three Stochastic settings.

- Fetches each ticker's OHLC **once** (`auto_adjust=False`, same as `backtest_signal.py`) and resamples to weekly **once** (`stoch_scan.resample_weekly()`, extracted from `compute_kd()` for this reuse) — the parameter grid then loops purely over cached in-memory weekly frames via `compute_kd_fast()` (same math as `compute_kd()`, just skipping the redundant resample per combo). This is what keeps a few-hundred-combo sweep to minutes instead of hours.
- Output: `OUTPUT/StochSignal_Sweep_YYYY-MM-DD.csv` — one row per combo (`stoch_length`, `k_smooth`, `d_smooth`, `total_trades`, `closed`, `open`, `win_rate_pct`, `avg_win_pct`, `avg_loss_pct`, `total_pnl`), sorted best-first. Console/log also prints the top 10 and the single best combo's `periodK`/`smoothK`/`periodD` values in Pine-input terms, ready to type into the indicator on the actual chart for visual confirmation.
- `tests/test_backtest_signal_sweep.py` verifies `compute_kd_fast()` produces identical output to the canonical `stoch_scan.compute_kd()` for several parameter combos on synthetic data — regression insurance that the resample-once optimization never silently diverges from the tested calculation.
- **Watch for grid-floor artifacts when picking a "best" combo.** The first sweep (`range(8,32,2)`) had every top-10 combo land on `length=8`, the grid's own floor — total $ P&L was still rising as length fell, so 8 wasn't a real optimum. Extending to `length=3` (see `LENGTH_GRID` history in the constant's comment) reproduced the same pattern at the new floor. Since length=3 is at (or one step from) the mathematical minimum for a Stochastic window, this was accepted as final rather than chased down to length=2. **Also distrust raw ranking-by-total-$-P&L for very-high-trade-count combos** — `k_smooth=2` variants at length=3 racked up 12,000–24,000 closed trades (vs. ~2,000 for the eventual winner) purely from firing more often; total $ P&L doesn't penalize trade volume, so those are noise-trading artifacts of the ranking metric, not genuinely better settings, even when they outrank cleaner combos.
